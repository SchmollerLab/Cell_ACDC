# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Python environment

Run code, tests and scripts with the Python of the development environment (Cell-ACDC with the GUI requirements, e.g. PyQt6, plus pytest), never a bare `python`/`pytest` from PATH that may be another interpreter. Machine-specific details (interpreter paths, other interpreters/venvs) belong in `CLAUDE.local.md` next to this file (git-ignored, one per developer); if it is missing, ask the user which interpreter to use. Run Python/pytest from this repo's root with `python -m ...` (puts the cwd first on `sys.path`, so this checkout is imported even if the environment's editable install points to another clone); scripts run from elsewhere (e.g. the scratchpad) need `PYTHONPATH=<this repo>`. Examples (`python` = the development environment's interpreter):

```bash
python -m pytest tests/test_phase_translator.py -q
python -m pytest tests -k "measurement_viewer"
python -m cellacdc            # launch main GUI
python -m cellacdc.measurements_viewer [folder]
```

## Project overview

Cell-ACDC (Cell segmentation, tracking and event annotation) is a PyQt (via `qtpy`) + `pyqtgraph` desktop application for live-cell imaging analysis, from the Schmoller lab (Helmholtz Munich). Package: `cellacdc/`. Install for development with `pip install -e .` plus `requirements_gui_pyqt6.txt` (or the `gui` extra). Version comes from `setuptools_scm` (`cellacdc/_version.py`, generated).

Entry points (`pyproject.toml`): `cellacdc` / `acdc` / `Cell-ACDC` → `cellacdc.__main__:run` (GUI, or headless CLI when `--params <ini>` is given, see `cli.py` / `_run.py`); `acdc-setup-models` → `cellacdc.service.setup_models:main`.

## Architecture

The codebase is large; many core files are huge single modules (`gui.py` ~31k lines, `apps.py` ~25k, `widgets.py` ~15k, `workers.py` ~7.5k, `myutils.py` ~6.5k). Search with Grep rather than reading whole files.

- **Launcher** — `_main.py` (`mainWin`): the main launcher window that opens the modules and utilities. Module buttons sit in stacked group boxes (`addModulesGroupBox` / `addModuleButton`, all in `moduleButtons`, heights set in `show`): Image preprocessing (data structure, data prep), Segmentation and tracking (automatic: segmentation and tracking module, correction: GUI), Measurements visualisation (measurements viewer, SpotMAX if installed). The buttons show no numbers, and docs and messages name the modules ("the GUI", "the data prep module"), never by number ("module 3"; user decision); `getting-started.rst` lists the button texts in launcher order (checked by `test_getting_started_lists_the_module_buttons_in_launcher_order`). `restoreDefaultButtons` restores `defaultTextDataStructButton`. `tests/test_launcher_layout.py` builds the real window with `myutils.setupLogger` / `mainWin.checkConfigFiles` patched.
- **Main GUI** — `gui.py` (`guiWin`): the annotation/correction GUI. It is composed of many mixin classes from `gui_navigation.py`, `gui_annotations.py`, `gui_custom_annotations.py`, `gui_viewer_tools.py`, `gui_overlay.py`, `gui_combine.py`, `whitelist.py`. Mixins are shared with other windows, so changes there affect multiple windows. When merging `main`, its edits to methods that this branch moved out of `gui.py` show up as delete/modify conflicts in `gui.py`: port them into the mixin version (find it by method name) instead of re-adding the method to `gui.py`; main's new methods next to them go into the same mixin, with main-GUI-only attributes the viewer would reach (e.g. `titleLabel`) read via `getattr`. Keeping the branch side of such a hunk can also drop main's last lines of the *preceding* method that stays in `gui.py` (happened to `update_z_slice`), so afterwards compare every `guiWin` method main changed across merge base / `origin/main` / working tree (`gui.py` or its mixin) with an `ast` script. Host-specific behaviour of shared code goes through hooks with main-GUI defaults, e.g. `ShortcutsGuiElements.showDeleteObjectShortcut`, `CustomAnnotationsGuiElements.canDeleteSavedCustomAnnot()` / `customAnnotColumnRemovalNote()` / `customAnnotColumnConflict()` (names refused on add/load, in the viewer already on OK of the dialog via its `columnConflict` callable; the viewer's configuration load and Open folder check the new tables first with `measurements_viewer_utils.flag_column_conflicts`), the optional `bottomLayoutFont` read by `gui_overlay`, and `limitToLoadedColumns` of the combine dialogs (`True` only in the viewer). `guiWin.connectScrollbars` connects the z-slice widgets' signals only for z-stack data and never disconnects them, so after a z-stack, 2D data in the same window still reaches z slots through keys that step the z-slice scrollbar (Up/Down, Home/End, ...): such slots must return early without z-stacks (`isZsliceScrollBarActive`; `segmInfo_df` is None then). In the viewer, positions never displayed have no `allData_li` (created by `initPosAnnotData`): mixin loops over `self.data` must tolerate it (`setAllIDs`, `countObjectsSnapshots`). `labelsGrad.item.loadPreset` (-> `updateLabelsCmap`) rebinds `self.df_settings` (`saveState` copies): never keep a local reference across LUT changes (`restoreDefaultSettings`). `changeMode` runs after the mode combo box changed (`currentText()` is already the new mode, the old one is `previousText()`), so methods gated on the current mode return early there for the mode being left (`askLineageTreeChanges` skips that check with `isLeavingMode=True`).

## Plugin conventions (discovered by folder name)

- **Segmentation models** — `cellacdc/models/<Name>/acdcSegment.py` with a `Model` class exposing `__init__(...)` and `segment(image, ...)` returning a label array. Init/segment keyword arguments with defaults become GUI parameters. Folders starting with `_` are ignored. See `models/thresholding/acdcSegment.py` for a minimal example.
- **Trackers** — `cellacdc/trackers/<Name>/<Name>_tracker.py` with a `tracker` class and `track(segm_video, signals=None, ...)`.
- **Promptable models** — `cellacdc/promptable_models/<name>/` (isolated env `_acdc_<name>` with `-` → `_`). `micro-sam_v1` = SAM1 models of micro-sam (`vit_*`), imported only from `micro_sam.v1` (micro-sam >= 2.0; its top-level modules are SAM2, 1.x has no `v1`); `micro-sam_v2` = SAM2 models (`hvit_*`, `micro_sam.v2`; z-stacks propagated by `PromptableSegmentation3D` on the lazily loaded video predictor). Both share the prompt handling of `promptable_models/micro_sam_base.py` (subclasses implement the `_segment_image_objects` generator); `tests/test_microsam_v{1,2}_promptable_model.py` fake micro-sam. Import micro-sam lazily inside functions: the GUI reads the module's parameters in the main env, without micro-sam. To check against the real micro-sam without touching the dev env, use a scratch `python -m venv --system-site-packages` venv of it + `pip install micro_sam` (with `MICROSAM_CACHEDIR` in the scratchpad).
- **Measurement processing** — `cellacdc/measurement_processing/<Name>/acdcProcess.py` with module-level `name` and a `Model` class with flags `is_timelapse`, `is_bulk_processing`, `numeric_input` and a `@staticmethod` `run(...)` (`Model` is never instantiated; a non-static `run` is skipped at load). See `SmoothMeasurement`. Recipes in configurations reference the module `name` (e.g. `"Ramp detection"`), not the folder name. NumPy-style `run` docstring parameters become the per-option info buttons; JSON kwargs are passed without type conversion, but recipe INI files store every kwarg as a string: cast them with `MeasurementProcessingParamsWidget.castRecipeValue` (bools via `ConfigParser.BOOLEAN_STATES`), never `bool(str)`. Plugins that fail to import, lack a non-empty `name` or `Model.run`, or repeat a `name` are skipped with a `RuntimeWarning` (first wins); `_load_processors(folder, package)` can target a tmp package in tests. Existing: `SmoothMeasurement`, `MinMaxNormalization` (fixed constants), `RampDetection` (FUCCI ramps, used by `fucci_cell_cycle.json`).
- `measurement_processing.apply_recipe(df, cols, recipe, new_colnames)` appends one output column per input and rejects mismatched, duplicate or already existing output names; `workers.MeasurementProcessingWorkerGUI` is one-shot (`setupJob` + `runJob`, result via `sigDone`).

## Data layout

Experiments are organized as `<exp_folder>/Position_<n>/Images/` containing `<basename><channel>.tif`, segmentation `<basename>segm*.npz`, the annotations/measurements table `<basename>acdc_output*.csv` (one row per `frame_i` × `Cell_ID`), and metadata CSV/JSON files. `acdc_df` in code refers to the `acdc_output` table (indexed by `frame_i`, `Cell_ID`).

Every save also writes a snapshot to `Images/recovery/<basename>acdc_output.zip` (`load.store_copy_acdc_df`). The archive keeps about 21 `iso<timestamp>.csv` members and drops the oldest, so diffing consecutive members shows when bad values first appeared. Each save re-reads every member and casts it with `pd_bool_and_float_to_int_to_str`. A traceback printed during a save can therefore come from an old member rather than the table you just saved.

## Testing

- Tests live in `tests/` (pytest; config in `pyproject.toml`: `testpaths = ["tests"]`, registered markers with `--strict-markers`, `faulthandler_timeout`, DeprecationWarnings ignored). Shared helpers in `tests/utils/`, sample data in `tests/test_data/`.
- Test tiers (issue #1314; contributor docs: "Running the tests" in `contributing.rst`): markers `slow`, `smoke` and `flaky` (`pyproject.toml`). Pull request pushes run `-m "(smoke or not slow) and not flaky"` on every platform (`build-*.yml`, the required `build (3.x)` checks) and, once on Ubuntu, the slow and flaky tests of the test files `tests/related_tests.py` relates to the changed files (job `related-tests`, not required); pushes to `main` and the Monday cron run the full suite in the same `build` jobs; before merging, the PR label `full tests` (or Actions > Full test suite > Run workflow, on a branch that contains `full-tests.yml`) runs the full suite on every platform (`full-tests.yml`). A plain `pytest` runs everything; locally the push tier is `python -m pytest -m "(smoke or not slow) and not flaky"` and the tests related to your changes `python tests/related_tests.py --run [pytest args]` (never `pytest $(python tests/related_tests.py)`: an empty selection runs the whole suite).
- When adding tests (issue #1314: the push tier must stay at a few minutes): run the new tests with `--durations=0` and mark `@pytest.mark.slow` each test whose setup + call + teardown takes 0.5 s or more, or whose parametrized cases take 5 s or more together (the threshold that keeps the push tier at about 4 min locally; a module fixture's setup is charged to the first test of the file: judge that test by its call time); `pytestmark = pytest.mark.slow` (a list when combined with other module marks) only when every test of the file is slow. `smoke`: only a test covering a core workflow (app/launcher/GUI start, loading a Position, viewer load and plot, configuration round trip, ...) that the smoke set does not cover yet; keep `pytest -m smoke` at about a minute. `flaky`: only with CI evidence (run ids in a comment), as a stopgap until fixed, never to hide a deterministic failure. Every test must pass in every tier: never depend on an earlier test of the file (module state, caches, "requires test_x to run first" skips), since deselection removes them. For `related_tests.py`, import the module a test covers directly (not only through `gui`) and name the data files it reads (e.g. a template's stem). The push tier prints `--durations=25`: an unmarked test listed there with 0.5 s or more needs the slow marker.
- Qt tests create a module-scoped `QApplication.instance() or QApplication([])` fixture and drive widgets with `QTest`; dialogs that would block are monkeypatched (see `tests/test_measurement_viewer_configuration.py`). No pytest-qt.
- Scratch Qt tests/scripts outside `tests/` (e.g. in the scratchpad) do not load `tests/conftest.py`: without `QT_QPA_PLATFORM=offscreen` their windows pop up on the user's screen and an `exec_` waits for the user (seen with a subagent's scratch test), and dialogs' `saveLastSelection` overwrites the real `.acdc-settings/last_selected_measurements.ini`. Put scratch test files in `tests/` temporarily (delete them afterwards) or run them with `-p tests.conftest` (from the repo root), and tell subagents the same.
- UI tests must run offscreen and never block (user requirement): `tests/conftest.py` sets `QT_QPA_PLATFORM=offscreen` (override the env var to watch the UI) and a watchdog auto-answers any dialog still blocking after 0.3 s (OK/default button, `ok_cb`, accept), reported as `AutoAnsweredDialogWarning` (handles `myMessageBox`, plain `QMessageBox` and other dialogs; see `tests/test_conftest_dialog_watchdog.py`). Still monkeypatch dialogs whose answer matters. Tests that run a real worker `QThread` under `exec_` request the `_auto_answer_blocking_dialogs` fixture and call its `.stop()` (else the watchdog answers the progress window); to test a utility's error path patch `utils.base._critical_exception_gui`, never replace `workerCritical` (it closes the progress window). The conftest also redirects user settings (`settings_folderpath` and the module-level settings/metadata/recent-paths/shortcuts/custom-annotation paths, `logs_path`, QSettings) to `tmp_path` (autouse `_isolate_user_settings`; only the names in its `USER_SETTINGS_PATHS`, so add new module-level paths inside the settings folder there, e.g. `saved_promptable_models_path`), and after each test destroys `deleteLater()`'d widgets (`flushDeferredDeletes`; outside an event loop `processEvents()` never deletes them), then hides top-level dialogs still left visible (`LeftOpenDialogWarning`: CI runs all files in one process, where a leaked dialog was answered by later tests' watchdogs). Then, once pytest released the fixture values (`pytest_runtest_protocol` hookwrapper), it collects again after a 1 ms event-loop pass (PyQt releases the slot proxies of deleted widgets only in an event loop) and freezes the objects still alive (`gc.freeze()`; the whole heap is collected after the last test of each module, or after every test with `ACDC_TESTS_FULL_GC=1`): a whole-heap `gc.collect()` per test took up to 0.5 s late in a session and was half of the suite's time. Freezing in a fixture teardown instead kept every test's windows alive until the module end (`test_fixture_window_of_previous_test_collected`). Objects that survive a test (module fixtures, caches) and become cyclic garbage in a later test of the module are collected only at the module end: create what a test checks with `weakref` inside that test. Import `cellacdc` GUI modules at the top of test and scratch test files: a module first imported inside a test body escapes the redirection, and building `guiWin` there overwrote the real `.acdc-settings/settings.csv`, `shortcuts.ini` and the saved window geometry.
- Icons in tests come from the committed `qrc_resources_<scheme>.py`: the runtime copy `cellacdc` registers on import (`cellacdc/qrc_resources.py` or `~/acdc-appdata/qrc_resources.py`) is refreshed only at app start (`_run._setup_app`), so the session fixture `_register_committed_qrc_resources` re-registers the committed module when the copy is stale. Local renders use the user's scheme (dark icons are light-colored: draw them on a dark background).
- Keep tests fast (user requirement): a test file should take seconds, not minutes. Use small synthetic tables (tens of cells/frames), keep parametrized grids and random parity/fuzz cases to a handful, avoid long `qWait`s, and check new tests with `pytest --durations=15`. Benchmarks and large fuzz runs belong in scratch scripts run with a timeout, not in the suite. The full suite takes about 13 min locally, the push tier about 4 min; slowest files (45-95 s each): `test_model_server.py`, `test_measurement_viewer_configuration.py`, `test_measurement_viewer.py`, `test_segm_worker_thread.py`, `test_timepoint_identifiers.py`.
- Never assert inside a `QTimer.singleShot` slot in tests: an exception there aborts the whole pytest process. Record values in the slot and assert after the blocking call returns.
- After `deleteLater()` PyQt may collect the Python wrapper of a parented widget before Qt deletes it, so `findChildren(<Python subclass>)` misses it: count such widgets by `objectName` (`test_nested_editors_are_deleted_after_use`).
- Lambdas/partials connected to signals of deleted widgets (they often reference the dialog) are released only in an event loop: to check with a `weakref` that a deleted dialog freed a table, run `flushDeferredDeletes()`, `QTest.qWait(10)`, `flushDeferredDeletes()` (`test_recipe_dialog_is_deleted_after_use`).
- The identity `Dummy` measurement processor is test-only (`tests/utils/measurement_processing.py`); tests get it through the `dummy_processor` fixture.
- Some tests need optional model environments/GPU/network (`test_all_model_environments.py`, `test_gpu_availability.py`, `tests/segm`, `tests/prompt_segm`); prefer running targeted test files.
- Local lint: flake8/pyflakes are not project dependencies: `pip install --target <scratch> flake8`, then `PYTHONPATH=<scratch> python -m flake8 --select=E9,F63,F7,F82 <files>` (the CI check) / `-m pyflakes <file>`; `python -m py_compile <file>` for a quick syntax check.
- Run Qt test files one at a time (`pytest tests/<file>`): since the conftest flushes deleted widgets, one pytest process over the whole suite also passes (as in CI), but a crash there may not print a summary.
- The measurements viewer's recipe dialog offers only measurement leaves of a hierarchical model (group headings are not selectable); tests select leaves by name and must enter a non-colliding output suffix before `ok_cb()`.
- Importing `cellacdc.measurements_viewer` in a bare `python -c` script prints a caught `regionprops.py` traceback (`app.mainWindow`) but works; smoke-test widgets through pytest instead.
- CI (`.github/workflows/`) runs `flake8 --select=E9,F63,F7,F82` (syntax errors / undefined names must not occur) and `pytest` (in tiers, see above) on Python 3.10–3.13: PyQt5 and PyQt6 on Windows and macOS, PyQt5 only on Ubuntu. The setup steps (Python, Xvfb on Linux, dependencies) are the composite action `.github/actions/setup-cellacdc`. The `main` ruleset requires the check names `build (3.10)`–`build (3.12)`: keep the job id `build` and its python-version-only matrix in `build-*.yml`, because a reusable workflow (`build / ...`) or another matrix dimension renames the checks and every PR then waits for the old names. A non-matrix job skipped by `if:` counts as passed for a required check, while the expanded names of the skipped matrix job `full (...)` of `full-tests.yml` never report (requiring them would block every PR until its full suite ran); a merge queue (`merge_group` trigger) would be the other way to enforce the full suite. The `build` jobs time out after 30 min on pull requests, `related-tests` and full-suite jobs after 90 min: hung Qt worker threads (`test_measurement_viewer_last_frame.py`) used to run until the 6 h default; `faulthandler_timeout = 300` prints every thread's stack when a test runs over 5 min.
- Platform pitfalls seen in CI: on macOS shortcut texts use macOS key names (`KeySequenceFromText.toString()`, `ShortcutLineEdit` display text, `ShortcutEditorDialog.new_hard_shortcuts` give `Command+O`; `ShortcutLineEdit.text()` gives `Ctrl+O`), so compare `QKeySequence`s or use `widgets.windowsShortcutToMac` in tests, and simulate with `monkeypatch.setattr(widgets, 'is_mac', True)`; macOS ignores `QMessageBox.setWindowTitle`; Qt5 `QAction.trigger()` emits `triggered` even for a disabled action, so handlers must not assume loaded data; Windows CI checks out on `D:` while tmp is on `C:` (`os.path.commonpath`/`relpath` raise `ValueError`); Python 3.10/3.11 `tokenize` recovers from errors (e.g. an apostrophe in a backtick name) that 3.12+ raise on. `QMutex.unlock()` on an unlocked mutex segfaults with Qt5 (Qt6 tolerates it, so the local PyQt6 env hides it): release "maybe locked" mutexes with `tryLock()` + `unlock()` (as `workers.worker_exception_handler` does). Never call `self.sender()` in helpers that also run outside slots, nor in slots that code, tests or the conftest watchdog call directly (`dialog.ok_cb()`): PyQt5 then returns the last proxy sender, possibly deleted, and touching it segfaults depending on test order (Ubuntu CI: `_updateMothBudLineSize` from `restoreDefaultSettings`, `QDialogListbox.ok_cb` in PR #1308); pass the object explicitly instead (e.g. `partial(slot, button=...)`). To test Qt5-only triggers of disabled `QAction`s on PyQt6, use `_Qt5LikeAction` (`tests/test_gui_mixins.py`). CI fonts are wider than the local ones, so layouts get squeezed: reproduce with a larger app font (e.g. `QApplication.setFont` at 18pt). A widget added to a shown window (e.g. in a new toolbar) is shown later by a queued layout, and `setFocus()` before that is lost if the focus moves meanwhile (e.g. a squeezed toolbar hides its focused widget): `processEvents()` and check `isVisible()` first (`_add_toolbar` in `tests/test_keep_ids.py`). On macOS with Qt 6, offscreen makes a shown `QMenu` the active window, so after closing it no window is active.
- pyqtgraph: `pyproject.toml` (and the `_run.py` startup check) still allow `>=0.13.7` and the requirements files are unpinned, but CI and new installs get 0.14: guard 0.14-only APIs with `hasattr` (e.g. Subtract Mean: `PlotDataItem.setSubtractMeanMode`, `PlotItem.updateSubtractMeanMode`, `ctrl.subtractMeanCheck`). To test 0.13.7, `pip download --no-deps pyqtgraph==0.13.7` into a scratch folder, unzip it and run pytest with `PYTHONPATH=<that folder>`.
- To test PyQt5 / Python 3.11 locally: make a venv from a Python 3.11 interpreter (local one: `CLAUDE.local.md`) and `pip install pytest -e . -r requirements_gui_pyqt5.txt`. On Windows, showing a plain `QMessageBox` with Qt5 on the offscreen platform crashes the interpreter (also in CI, killing the whole pytest run): tests that show one get the `shows_qmessagebox` skip mark (`test_conftest_dialog_watchdog.py`); use `QT_QPA_PLATFORM=windows` to run them locally.

## Code style notes

- Use `qtpy` imports (not `PyQt6` directly) so PyQt5/PyQt6/PySide all work.
- `toolbar.addAction(action)` returns None (PyQt5 and PyQt6): get the button with `toolbar.widgetForAction(action)` (as `widgets.ToolBar.addButton`), e.g. for `widgetsForActions` (a None there broke launching the main GUI; `tests/test_gui_launch.py` runs the real `guiWin.run()`).
- GUI code uses Qt-style camelCase method names; newer non-GUI modules (predictors, phase translator) use snake_case functions and class-based APIs with thorough docstrings.
- Keep module docstrings in sync when changing behavior of the measurements viewer and predictor modules—they serve as the specification.
- Qt fires a button's own shortcut (`QAbstractButton.setShortcut`) only while the button is visible, and an overflowing toolbar (small screens) hides the buttons that do not fit (toolbar `QAction`s keep working). `widgets.ToolBar` covers buttons added with `addWidget` (`_ToolBarOverflowShortcut`: a toolbar `QShortcut` enabled only while the button is hidden by the overflow, its action visible and the button enabled; never both at once, or Qt triggers neither). So put shortcut buttons in a `widgets.ToolBar`, hide them via the action returned by `addWidget`, and after changing a button shortcut outside `setShortcuts` call `ToolBar.updateOverflowShortcuts()` (`tests/test_toolbar_overflow_shortcuts.py`). Key handlers that require a visible tool (brush/eraser `keyPressShortcut` in `keyPressEvent`) must also accept `ToolBar.isWidgetHiddenByOverflow(button)`.
- Main GUI keys chosen in dialogs (custom annotations, points layers) are refused when any action/tool of the window uses them in any mode (`guiWin.reservedShortcuts`, also the overlay digits 0–9 and the "Delete object" key of `delObjAction`; passed as a callable, evaluated on OK because both dialogs leave the window usable, by `customAnnotationDialogKwargs` and to `AddPointsLayerDialog(reservedShortcuts=)`; `getHardcodedShortcuts` lists them so the shortcut editor flags tool keys that clash). Add keys handled in `keyPressEvent` (also modifier combinations, e.g. Ctrl+Up/Down of the overlay segmentation opacity) to `guiWin.KEY_EVENT_KEYS`. Annotations loaded with a position keep their key unchecked.
- Tool tips: Qt never wraps plain-text tool tips, so keep each line ≤ 80 chars (`qutils.TOOLTIP_MAX_LINE_LENGTH`). Lines of a paragraph must be about equally long (user feedback: clause-by-clause breaks look ragged): fixed texts get explicit `'\n'` where `qutils.balanced_wrap` puts them (paragraph joined, then wrapped; title, list items and `Shortcut:` lines stay separate), tool tips with user content (names, equations, predictor `describe()`) go through `qutils.wrap_tooltip` (balanced) without manual breaks inside sentences; rich text needs a tag on its first line (`qutils.might_be_rich_text`). Keep first lines that name text-less widgets and `Shortcut: "<keys>"` lines (rewritten by `setShortcuts`) intact. Viewer tool tips are checked by `tests/test_tooltip_line_length.py`.
- Main branch for PRs: `main`.

## GitHub

- The required `build (3.x)` checks run only the push tier of the tests: before merging a PR, add the `full tests` label (`gh pr edit <pr> --add-label "full tests"`) and wait for the "Full test suite" checks (`full-tests.yml`, only for PRs into `main`, as the `build-*.yml` checks).
- `gh` older than ~2.82 (installed with winget) fails in `gh pr edit` with "Projects (classic) is being deprecated" (GraphQL): upgrade with `winget upgrade --id GitHub.cli` (2.105 works).
- PRs targeting another PR's branch (e.g. a fix on `signal_gui`) are native GitHub stacks: every PR is checked against `main`'s ruleset (1 approval after the last push, builds, merge commits only; "review required" even though `signal_gui` has no rules), merges go bottom-up, admin bypass merges only the bottom PR. Update a stacked branch by merging its base and pushing: the server-side "Rebase stack" force-pushes, and replaying merge-updated branches conflicts (CLAUDE.md notes).
- A stack's conflicts with `main` show only on its bottom PR (`mergeStateStatus` DIRTY; upper PRs are checked against their own base and show CLEAN, but carry the same conflicts): merge `main` into the bottom branch, resolve there, then merge each branch into the one above. "Stack #N" is not a PR number: `gh api repos/<owner>/<repo>/pulls/<pr>` has `stack` (`number`, `position`, `size`, recorded `base.sha`). Trial-merge without touching the shared checkout: `git merge-tree --write-tree --name-only <branch> <other>`.

## Long-running work

- When a background process (workflow, subagent, pytest run, script) runs longer than ~10 minutes, check on it about every 10 minutes with cheap reads instead of only waiting for its completion (user request): file modification times and the last entries of the workflow `journal.jsonl` / `agent-*.jsonl` transcripts, log tails, running `python.exe` processes (`Get-CimInstance Win32_Process`). Stop a hung process (no output for minutes, waiting on its timeout) and continue without it; a resumed workflow reuses its finished agents.
- Workflow `agent(..., {isolation: 'worktree'})` fails in this checkout (the harness reads git's `C:/...` path vs its `c:\...` path as a redirect), and its worktrees start from `origin/main`, not the current branch. For parallel agents that edit files, create the worktrees yourself (`git worktree add -b <branch> <scratchpad>/wt/<name> <base branch>`), give each agent its path (its shell starts in the main checkout), then merge the branches and `git worktree remove` them.
- Give agents' and scripts' Python commands short timeouts (≤ 120 s): a scratch pytest that built a real `guiWin` and loaded a synthetic Position hung after "Counting total number of segmented objects" until its 300–600 s timeout, run after run. Test GUI annotation logic on a stub host that runs the real `guiWin` methods (`tests/test_gui_mixins.py`, `tests/test_normal_division_lineage_tree.py`) instead.

## Maintaining this file

When you learn something during a task that would have saved time or prevented a mistake, and it is likely to matter again, add it here before finishing the task.

**Add:** non-obvious conventions, gotchas, where an important piece of logic lives, how to run or test something, environment quirks, and corrections from the user ("don't do X", "always do Y").

**Don't add:** what is obvious from reading the code, one-off task details, git history, or anything temporary. Keep entries to one or two lines and point to files (`module.py` / `ClassName`) instead of copying code.

**How:**

- Machine-specific notes (interpreter paths, local environments, installed tools) go in the git-ignored `CLAUDE.local.md`, not here.
- Put each entry in the section it belongs to (Architecture, Plugin conventions, Data layout, Testing, Code style). If none fits, create a new `##` section rather than appending to the end of the file.
- Update or delete an existing entry that is outdated or wrong; never keep two entries that contradict each other.
- If an entry describes a whole subsystem and grows beyond a few lines, put the details in a doc next to the code (like `cellacdc/code_structure.md`) and link to it from here.
- In your reply to the user, say briefly what you added or changed in this file.
